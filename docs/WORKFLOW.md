# Workflow: from idea to ladder

All commands run from the repo root. Python scripts run with `python -I`. On Windows, run shell scripts with Git Bash (`"C:\Program Files\Git\bin\bash.exe"`). In PowerShell, `bash` is WSL, which has no Python.

## Setup

- Install the CLI: `pip install cambc`. It is not on PATH; every tool calls it through `tools/cambc.ps1` or the full path in the Python scripts (`%LOCALAPPDATA%\Packages\PythonSoftwareFoundation.Python.3.11_...\Scripts\cambc.exe`). If your path differs, change it in one place per script (search `cambc.exe`).
- `powershell -File tools/cambc.ps1 login` once, then `... maps pull` to refresh `maps/`.
- Engine version is pinned in `cambc.toml` (`sdk_version`). After a CLI upgrade, run `cambc init` in a scratch folder and copy `sdk/` and `cmake/` across.
- Build check: `powershell -File tools/cambc.ps1 build main --release`. Bot names are paths under `bots/` (`main`, `pool/hb4`, `exp/x1`).

## The loop

1. **Find the factor.** Compare us with the teams near us on the platform. Decode a panel run (`bash tools/replay/decode_run.sh RUN@PANEL [JOBS]`, Node 22, about 4 minutes for 50 games at the default 3 jobs; see "Local quirks" for more). Count the decoded games against the run's games: on 10-25 a fifth to two fifths of each run's replays failed to download while gates ran, until `gdl.py` got retries; running `gdl.py RUN` again fetches only the missing files and measure us vs them with `python -I tools/replay/decoded.py CMD data/fights/RUN_PANEL` (`gems`, `fights`, `channels`, `types`, `items`, `risk`, `sources`). The older summary tools (`cgold`, `cdmg`, `fight`, `tline2`, `early3` on `gdl.py` downloads) still work. Pick the one factor where we lack most. Name a **target metric** (for example "champion damage per game by r800") before writing code.
2. **Make a variant.** `python -I tools/variant/mkvar.py main exp/NAME FILE "OLD" "NEW" [...]`. Each OLD must match exactly once. For logging, also run `tools/variant/mklog.py exp/NAME` (the convention is to add the suffix `l`).
3. **Debug it locally.** Add temporary prints, run one game, and confirm the rule fires. Then remove the prints.
4. **Local run.** `python -I tools/local/multi.py exp/A,exp/B --jobs 6`. The default is all 40 maps x 7 pool bots x 2 sides = 560 games per candidate. Compare with the base on the same run. Current base `main` is `cp3` (2026-10-25): 406/560 (`pool/dr3` 391, `pool/fe1` 414 on an older pool run, `pool/hb4` 384). For a quicker breakage check use `--pool pool/b_log,pool/pd1,pool/tf3` (240 games, about 43% of the time): `cp3` scores 184/240 there (`dr3` 180, `fx1` 188, `hb4` 176). Local runs do not judge fight, item or banking changes; check those with decoded platform replays (`docs/findings.md`). A variant goes to the platform only after it passes this local run against a bar written before it (user, 11-02: a local failure stops the variant; a local pass does not prove it). Add `pool/fe1` with `--pool` to test against the previous ladder bot.
5. **Platform gate.** Use a batch panel from `results/panels/` (README there), ideally `b56`-style combined panels of about 90 games in one gate (one upload). Write a plan of `BOT RUN PANEL` lines and run `bash tools/platform/gatechain.sh PLAN [CUTOFF]` in the background: it runs the gates one by one and refuses to start while another gate runs. On a pinned panel (name ending in `p`, see the next section) the run that supplied the group ids is the base and no base line is needed. On an unpinned panel put a base line `main base_NAME PANEL` in the same plan (main is not uploaded again), because opponents change bots over the day. Give every run a unique name (rcmp trap below). The old small gate (`gate.sh exp/NAME`, 20 games against panel 8) still works but is too small to decide anything.
6. **Compare.** `python -I tools/platform/rcmp.py BASE@PANEL NEW@PANEL` pairs games by (opponent, map) and prints wins, flips (L->W, W->L), margin per game and a sign-test p-value. Separate runs can be joined to match a combined panel: `rcmp.py "A@b5+B@b6" C@b56`. Then decode both runs and compare the target metric with `decoded.py`.
7. **Decide.** Accept only if the target metric moved and the wins are not worse beyond noise (about 3 wins per 50 games between two variants; see "What the evidence says"). Write the decision rule down before the result comes in. `bash tools/platform/adopt.sh NEW OLD_NAME` moves the old main to `bots/pool/OLD_NAME`, copies `bots/exp/NEW` over `bots/main`, build-checks and submits it. Add one row to `docs/experiments.md` for every variant tested, accepted or not, then delete `bots/exp/NAME`.
8. **Ladder.** `powershell -File tools/cambc.ps1 submit main`. The bot submitted at the Sprint lock time is the tournament bot.

## What the evidence says about testing

- **Local results do not predict the platform for fighting.** The local pool is our own old bots. Changes that make us fight more (pa1, lf1, hc2, k_danger0) won locally and lost on the platform. Changes to items, draft and danger settings also failed to transfer. Use local runs as a filter against breakage, and for economy-only changes.
- **Platform games are nearly deterministic.** The same bots on the same map give the same score. A same-bot rerun 1.5 h later flipped 0-3 of 20 games. Run-to-run drift comes from opponents changing their bots, so always run the base at the same time. Against a single opponent that did not resubmit, the base is exactly repeatable: hb4 vs AlphaSlop gave identical 40-game results 2.5 h apart (hb4_a and hb4_b @r30). **Drift check:** re-run a bot that changes little (or main) and count identical game scores. On 10-25, dr3g matched dr3's b6 run from 3 hours earlier in 29 of 40 scores but its b5 run from 9 hours earlier in only 19 of 50 (b5 score 23 became 21).
- **Pinned panels remove opponent drift** (CLI 4.0.0, 2026-10-26). `cambc match-groups create TEAM --source-group GROUP_ID` makes the opponent play the bot it used in that earlier match group. A pinned panel (`results/panels/specs_b9p.txt`) ends each group with the group id of one base run (`main1026h_b9@b9`), and `gate.sh` passes it on. Because games are deterministic, that base run is then the exact base of every later run on the panel: all 120 games count, none is dropped for a changed opponent, and no closing base run is needed (half the quota of the old base-variant-base chains). On b9, main1026g and main1026h gave identical scores in all 80 games of the 8 opponents that kept their bots. **Pin checked** (10-26 12:19): main replayed main1026g's group against smurphy (5 games) pinned to that group, after smurphy had changed bots, and repeated all five of main1026g's games exactly (scores, rounds, deaths), not main1026h's. Re-pin at least daily from a fresh unpinned base run, so the panel keeps up with the opponents' current bots.
- **50-game panels are noisy.** Eight near-identical variants on the same 50 b5 games: 17 games lost by all, 7 won by all, 26 swing; about 2.2 wins of chance per run, about 3 between two variants. A change that rarely fires leaves almost every game identical (rg1 vs fh1: 1 of 50 changed), so the noise comes from changes that alter behaviour broadly. Decide with continuous decoded metrics (damage, deaths, gems tributed and lost) and with games every variant loses.
- **Code changes flip games chaotically.** A pure bug fix (hc3) went 2 up, 5 down. A 20-game gate is noisy: treat ±3 wins as noise and look at the margin and flips.
- **Never pick games by past result.** Replaying only the games we lost (the "lost-match spec") showed big gains that vanished on the full panel (bt1: 32/75 on the lost set, 40/100 vs 41/100 full). That was regression to the mean.
- **Local noise:** a no-op change (removing prints) moved 80-game results by 9 wins. Trust 560-game runs, and treat differences under about 10 wins as noise.
- **Optimisers overfit.** Tuning constants against the starter bot (`opt.py`, deleted) produced a bot that scored 15/90 on the platform.

## Platform quirks

- Upload limit: **20 bot submissions per hour** (HTTP 429). A gate plus the main resubmit is 2 uploads, so at most about 10 gates per hour. `gate.sh` aborts when its submit fails (otherwise the games run with whatever bot is on the platform), and `gateq.sh` requeues that gate and retries the main submit until it succeeds. A combined gate over both map sets (`results/panels/specs_bNc.txt`, 10 groups) tests a variant with one upload. A queued gate of `main` itself skips the upload (main is already on the platform). Never edit `gateq.sh` while it runs: bash reads scripts as it goes. (An edit that keeps every byte offset after the running line, such as a same-length in-place write, is safe: `gate.sh` got its `--source-group` field that way on 10-26 while a gate ran.) CLI 4.0.0 also has `cambc submissions list` and `cambc submissions activate N|latest`, which switch the live version without an upload; `gateq.sh` still re-uploads main.
- **Every teammate's upload can be read on the website** (found 11-02 19:30 IST): the Submissions page
  (`/game/submissions`, version history) has a "Code" button per version, a read-only viewer
  (`?version=N&file=src%2Fbot.cpp`) and a "Download .zip". The viewer reads `GET /api/v1/submissions/{id}/files` (list
  with sizes) and `GET /api/v1/submissions/{id}/file?path=src%2Fbot.cpp` (one file) with the browser's login;
  submission ids come from `cambc submissions list --json`. The CLI has no download command. The Chrome extension
  blocks code returned by its JavaScript tool ("Cookie/query string data"), so compare versions there by hash, or
  download the zip (ask the user first).
- **An upload takes the live selection** (checked 11-01 22:32 IST with `cambc submissions list --json`): right after `cambc submit`, `selected` is the new version (status `queued`) and `pinned` is false, so the upload goes live by itself once it compiles (about 1.5 minutes) and plays the ranked sets until another version is selected. `cambc submissions activate N` pins the selection again; done while an upload is still queued, it cancels that upload (status `cancelled`). So a gate that uploads exposes its bot from the compile to the restore: `gateq_live.sh` uploads only in the ranked window (x1:00-x2:59), and a second gate of the same code should select the version (`vN`) instead of uploading it again. A selection takes minutes to become `active`: `activate` returns at once, but on 11-01 the active version changed 2.5 to 5.3 minutes later (1485 selected 22:41:03, active 22:46:21 IST; restores of 1478 2.5-4.5 minutes). The delay is a new compile: a selected version that is not active goes back to status `queued` (1484 selected 23:41:03, `queued` from 23:49:27) and goes live after that compile, so the delay follows the platform's compile queue. A 90-game gate (about 6 minutes of games) plus the restore therefore always spans one ranked-set start, whatever the window. The submissions API is also rate limited (HTTP 429, "retry after N seconds"), seen at 22:33 while a replay download ran.
- Unranked quota: 50 match groups an hour. From 2026-10-25 a refused creation reads "Your team can start 50 unranked matches an hour" (HTTP 429, with a retry time); on 10-23/24 it acted like 50 per rolling 30 minutes. The window is a rolling hour: each group frees its slot 60 minutes after it was created, and `resetsAt` is when the oldest counted group ages out, not a full reset (10-25: at 20:40 used 50, resetsAt 20:55:45; at 21:01 still used 50, resetsAt 21:09:52). `cambc match-groups quota --json` shows `limit`, `used` and `resetsAt`. A group must have exactly 5 different maps ("Choose exactly five different maps", HTTP 400, for 5x boss_battle on 10-25); `--sides a,b,a,b,a` sets our side per game. A b3456 gate (140 games) is 28 groups, so under two fit in an hour: size a chain to the quota (six such gates take about 3.5-4 hours). `gate.sh` retries a refused creation every 30 s. `tools/platform/qwait.sh N` waits for N free groups. Other teams can also queue unranked games against us; those use their quota.
- Gates submit the bot. Never run two gate chains at once, because the second submission replaces the first bot mid-gate. In Git Bash, `ps` does not show command lines, so find and stop gates with `bash tools/platform/procs.sh [kill]`. Near a lock, stop every gate in time and make sure the last upload is main (after `gateq.sh` the last upload always is).
- Run names in `results/gate.log` are `BOT@PANEL[@OFFSET] groupid...`. Panels: `p8` = full panel (`gate_full.sh`, 10 teams at ladder ranks 60-69 on 2026-10-23), `p8s` = small gate. `GATE_OFFSET` shifts the map windows of the full panel. Opponent team ids are inside the gate scripts. Refresh them when the ladder moves.
- **rcmp cache trap:** `rcmp.py` caches results per run name in `data/cache/res_<run>.json` and reads the last `gate.log` line with that name. Reusing a name (`hb4l@p8s` twice) silently reuses the old result. Give every base run a unique name, or delete the cache file.
- `gate.sh` submits the variant before it creates the match groups, and a full quota makes it retry every 30 s: a chain
  started while the hour's 50 groups are spent leaves the variant on the ladder for the whole wait (10-30 05:12: tw13b
  would have waited 24 minutes; the chain was stopped and main resubmitted). Start a chain when the quota has room
  (`cambc match-groups quota --json`: `used`, `resetsAt`; groups free up one hour after their creation).
- Pinned panels (`--source-group`) are deterministic: the same bot replays the same games (`docs/findings.md`, "Pinned
  panels are deterministic"), so a base run of main from earlier in the day serves as the base on that panel.
- Opponent teams without a bot for the current engine cannot be scheduled ("doesn't have an eligible bot", HTTP 409). The gates skip them.
- Platform stdout in replay bundles is NUL-padded per turn. Strip `\0` before splitting lines.
- Ranked matches run every 10 minutes with the currently submitted bot. Each gate puts a test bot on the ladder for its whole run, so a day of gating costs rating (2026-10-24: rank 76 to 82 between 11:30 and 15:15 while main itself was unchanged). Near a lock, gate less and leave main submitted.

## Local quirks

- Copying a bot with `cp -r` also copies `.cambc/`, which breaks the build. `mkvar.py` skips it.
- After editing a bot, if the build looks stale, delete `bots/X/.cambc`.
- Local replays fill the disk fast (a 560-game run with `--keep` writes several GB). `multi.py` deletes replays unless `--keep`. Clear `data/runs/` regularly, but never while a run is writing there (that lost most of a 560-game run on 10-25).
- Heavy runs get killed when RAM is low. The machine has 12 threads and 16 GB, usually 3-5 GB free. On 10-25 the quick pool at `--jobs 11` took 135 s with free RAM 0.4 GB lower, and gave the same result as at 6 jobs. Decoding (`decode_run.sh RUN 10`) needs about 140 MB per job (10 jobs: 3.1 GB free fell to 1.7 GB). Do not run both at full width at once. With under 2 GB free, use `--jobs 6`. Process creation can fail before physical RAM runs out: on 10-30 at 15:30-15:50, with two decodes (10 jobs together) and a local screen at 7 jobs beside the user's editors and browsers, the free commit (virtual) memory fell to 1.4 GB of 30 GB and Git Bash forks, ripgrep and Python spawns failed with `CreateProcessW failed ... errno 13` / `uv_spawn`; a gate's summary then counted only 10 of its 50 games (`panel_result.py`; the games themselves were complete). Check both numbers before a heavy run: `(Get-CimInstance Win32_OperatingSystem) | Select FreePhysicalMemory, FreeVirtualMemory` in PowerShell, and keep 3 GB of free virtual memory.
- The disk fills with run outputs: on 10-25 `data/summaries` (1 MB per platform game) held 20 GB and `data/runs` 11 GB, with 5 GB left on C:. Check `df -h /c` before long runs. On 10-26 at 13:25 only 485 MB were left (summaries 22 GB, runs 13 GB); deleting the run folders no doc names (`grep -rl multi-HHMMSS docs`) from before 08:00, and the `.tmp*` files older than an hour in `data/summaries` (interrupted downloads), freed 9 GB. At 14:45 the cached match summaries from before 10-22 (engine eras that no current analysis reads; `group.py` fetches a summary again when asked) were deleted: 7,796 files, 6.4 GB. On 10-29 at 13:45 C: was full again (1.3 GB left; summaries 11 GB, runs 7.9 GB), and a shell command died with Win32 error 1455 (the page file could not grow). Freed 12.7 GB at 14:10 (t9, at the user's request): the stale `.tmp*` downloads and the cached summaries from before 10-29 (8.6 GB; `gdl.py` and `fuel_events.py` fetch one again when needed), the run folders from before 10-29 that no doc names (0.2 GB), and every game JSON of the older runs gzipped in place (`*.json.gz`, 16 times smaller: 6.7 GB of JSON to under 0.5 GB; `gunzip` a run folder before `multi.py`-style readers use it). On 10-30 at 10:50 C: was full (0 bytes free): 48 of the 420 games of a local screen failed with "There is not enough space on the disk" (one `.error.log` per game in the run folder; `multi.py` counts only games with a JSON, so its summary showed 372 games and no error). Freed 12 GB by 11:02: the run folders from before 10-30 (a 420-game screen keeps about 430 MB of game JSON) and the summaries cached before 10-30. Check that a screen's summary shows all 420 games. On 10-31 at 20:20 C: had 2.7 GB free (summaries 7.9 GB, runs 3.2 GB, fights 3 GB): the raw platform replays from before 10-30 whose decoded copies in `data/fights` were complete went (0.7 GB), and the rest was compressed in place with `tools/local/compact_old.py` (transparent NTFS compression, about 15 to 1 on game JSON, readers unchanged): 14 GB free at 20:48. Deleting cached summaries needs the user's approval (the permission guard refuses it otherwise). On 11-04 at 01:20 IST C: had 8.9 GB left. Freed 16 GB at the user's request: 78 old `data/runs` folders, cached summaries from before 11-02 (11,007 files, fetched again when asked), scratch folders, `data/replays/platform` and `data/fights` of panels older than 11-03, and 36 `bots/exp` folders with a row in `docs/experiments.md`. Kept: the local bases (`multi-142332`, `multi-145148`, `multi-172019`, `multi-031107`, `pa_join`), runs named by live rules, and decodes of `rf1`, `e1531`, `ra2`, `e1536`, `vf3`, `q_all`, `s31`, `s35`, `nb*`, `tt1`. 34 older `bots/exp` folders have no row and were left.
- Some source files use CRLF line endings. Patch scripts must keep them (`mkvar`, `mklog` and `mklock` do). Git Bash `sed -i` writes a CRLF file back with LF endings (10-26, `docs/experiments.md`), and its `grep` does not see the `\r`: edit such files with the editor, or with Python in binary mode.
- `init_world` spreads over the first rounds (fuel). For init debug prints, run 40+ rounds.

## Team rules

- One factor at a time: list every gap against the teams above, pick the largest, and stay on it until matched.
- Before each step, ask whether it is needed and how the idea could be better.
- Prefer measured or learned formulations over hand-tuned constants (fit the constant on decoded platform games, write the fit next to the code).
- Judge fight, item and banking changes with decoded platform metrics, not local runs or 50-game win counts alone.
- Check the mechanism before the gate (user, 10-27): copy the variant to `bots/exp/<name>l`, print one tagged line per turn where the change should act (what it chose, and what happened: distances before and after, whether the cast or call went out), run 40 local games with `--keep`, and read them with `tools/local/probe_lines.py`. Give main's copy the same print for the comparison. The 10-27 probes (pb1, fw2, hw1, mr1) are in `docs/findings.md`, "Mechanism probes". Delete the probe folders afterwards.
- Platform tests: batch panels of 40-90 games since 10-24 (a 20-game small gate is within noise; use it only as a quick check).
- Ladder rating does not matter during testing. Bot quality does. Submit `main` again after tests if the deadline is near.
